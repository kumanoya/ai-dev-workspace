# verify-design-diff — AI 視覚検証（オプション工程）

`/fix-design-diff` で実装した画面のスクリーンショットを撮り、参照デザイン画像と突き合わせて相違点リストの解消状況を報告する。**人間が明示的に依頼した場合のみ実行するオプション工程**（既定は人間がブラウザで目視確認する）。**コードの修正は一切しない**。指摘を報告するまでで止め、無断で修正ループに入らない。

<!-- model: 画像2枚の比較を含むため、使用モデルが画像入力（vision）に対応していることが前提。非対応なら Sonnet 等に変更する -->

## 入力（チャットメッセージから拾う。無ければ先に確認する）

- **referenceImage**: 正しいデザインを示す画像ファイルのパス（正解）
- **diffList**: 元になった相違点リスト（各項目が解消されたか個別に判定する）
- **route** / **proto**: 対象画面のルートとプロトタイプ
- **sourceFiles**（任意）: 今回変更された実装ファイル群（数値プロパティの確認に使う）

## 1. 実装画面スクショの取得

- 対象プロトタイプに Playwright とスクショスクリプト `prototypes/<proto>/verify/screenshot.mjs` が導入済みであることが前提。出力先は `prototypes/<proto>/verify/shots/`（gitignore 済み。コミットしない。ディレクトリがなければ作る）。
- **dev サーバーの確保**: 起動済みか確認する（`curl -s -o /dev/null -w "%{http_code}" http://localhost:<port>`。port は `vite.config.ts` が権威）。**起動済みなら流用する**（新規起動はポート占有で失敗するだけでなく、他の作業を止めかねない）。起動していなければバックグラウンドで `pnpm run dev` を起動し、ready を確認する。**自分が起動した場合のみ**、スクショ取得後に停止する。
- **撮影**:
  ```bash
  cd prototypes/<proto>
  node verify/screenshot.mjs <route> verify/shots/<name>-impl.png --full
  ```
  出力 JSON の `ok:true` / `status:200` / `consoleErrors:[]` を確認する（コンソールエラーがあればスクショ比較より先にその報告を優先する）。
- **screenshot.mjs が無い環境のフォールバック**: スクショ工程をスキップし、「dev サーバーの `http://localhost:<port><route>` を直接開いて確認してほしい」と案内して終了する。スクショのために新たな仕組みを作り込まない。

## 2. 検証原則: ビジョンの限界を超えない

マルチモーダル AI は「要素の有無・配置・順序・文言・明らかな崩れ」の判定は得意だが、**「数pxの余白差」「わずかなフォントサイズ/ウェイト差」「微妙な色差」を画像だけで正確に測るのは苦手**（幻覚・見落としが起きやすい）。判定の根拠を2つに分ける:

- **画像を根拠にしてよいもの** … 要素の有無/欠落、順序・段組み、グルーピング、明らかな大きさ違い、折り返し・はみ出し・重なり、テキスト文言、全体の印象。
- **画像で目測してはいけないもの（= コードで確認する）** … 余白(padding/gap)・フォントサイズ/ウェイト・色(hex)・角丸などの**数値プロパティ**。`sourceFiles` や対象プロトタイプの `index.css` の `@theme` を読んで実値を突き合わせる。
  - 色差の疑いは必ずコード上のクラス/トークン/直値 hex で確認し、確認できないなら指摘にしない。

検証範囲は **`diffList` の項目＋今回の変更に起因する明らかな崩れのみ**。参照画像と実装の網羅的な差分探索はしない。

推測（コード未確認）の扱い: コード/トークンで裏が取れない数値・色の差は、**指摘にしないのが既定**。どうしても触れる場合は severity を `nit` とし、現在値の文頭に必ず「推測（コード未確認）:」と明記する。人間の目でも判別困難な微細差は報告しない（ノイズになる）。

## 3. 重大度と合否基準

- `critical`: `diffList` の項目が未解消、または要素の欠落・誤配置・文言誤りでデザイン意図が伝わらない。
- `major`: 明確に視認できるズレ（はっきり分かる色違い／要素のはみ出し・崩れ／大きく異なる寸法）で、画像で確実に判別できるか、コードで実値の差を確認できたもの。
- `minor`: 視認できるが影響の小さい差で、コード等で裏が取れているもの。
- `nit`: 好みレベル、または推測（コード未確認）。

合否: `diffList` の全項目が解消され、かつ `critical` と `major` が新規に **0 件**なら PASS。minor/nit のみなら原則 PASS（次回改善メモとして残す）。

## 4. 報告

1. 合否（PASS / FAIL）と全体所見（1-2文）
2. `diffList` の各項目の解消状況（項目ごとに ○/×）
3. 指摘の一覧（**重大度の高い順**。minor/nit も省略せず全件載せる — 取捨選択は人間の役割）:

   | # | severity | 領域 | 指摘 | 該当ファイル:行 | コード上の現在値 | 推定される修正 |
   |---|---|---|---|---|---|---|

4. 実装スクショのパスと参照画像のパスを併記する（人間が見比べる材料として）
5. 末尾に1行添える: *指摘の取捨選択と修正判断は人間が行ってください。修正指示はまとめて1メッセージで、実値つきでお願いします。*

## 制約

- **コードの修正は一切しない**（指摘のみ）。指摘があっても無断で `/fix-design-diff` を再実行しない。
- Figma 系 MCP ツールは使用しない。
- 各ファイルは原則1回だけ読む。同じ領域を何度も見直さない（コスト配慮）。
