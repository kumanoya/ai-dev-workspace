# fix-design-diff — 参照画像＋相違点リストによる実装修正

実装済み画面と「正しいデザイン」を示す**画像ファイル**（デザインツールからの書き出し PNG、デザイナー共有のスクショ等）を突き合わせ、人間が挙げた相違点リストを解消する。**デザインツール連携（Figma 系 MCP ツール等）には一切アクセスしない**（ツールが見えても使わない。コスト節約や未連携環境での利用を想定した意図的な構成）。

## 運用方針（最優先）

「安く・そこそこ直る」ことを最優先に設計されている:

- **相違点リスト（diffList）がスコープの全て。** 修正箇所の特定は人間の役割であり、AI は渡されたリストの項目だけを直す。作業中にリスト外の差異に気づいても修正せず、最終報告に1行メモを残すに留める。
- **画像は参考資料。** リスト項目を実装するときの見本として参照するのみで、画像と実装の網羅的な差分探索・照合はしない。
- **完璧を目指さない。** リストの項目がある程度解消されれば成功。判断できない項目は推測で直さずスキップし、最終報告に含める。
- **最終チェックは人間、確認はブラウザで。** 既定フローはスクショも撮らず、実装完了とブラウザ確認用 URL の案内までで終了する。AI による視覚検証が必要な場合は `/verify-design-diff` を別途明示的に実行する。

## 入力（チャットメッセージから拾う。無ければ先に確認する）

- **imagePath**: 正しいデザインを示す画像ファイルのパス
- **diffList**: 相違点リスト（箇条書き）
- **route**: 対象画面のルート（例 `/users/new`）
- **proto**（既定 `sample-app-v2`）: 対象プロトタイプ
- **targetHint**（任意）: 画面名・推定コンポーネントパス

色・数値系の項目は、可能なら具体値を含めてもらう（例「送信ボタンの背景を `#e3edfe` に」「カード間の gap を 16px に」）。具体値があればピクセルサンプリング工程が丸ごと省け、精度も上がる。

## 手順

1. **画像を読む**: `imagePath` を読み込み、`diffList` の各項目に対応する箇所だけを目視確認する（項目に関係ない領域の精査はしない）。
2. **対象実装の特定**: `targetHint` が具体的でなければ検索で該当する organism コンポーネント・データファイルを探す（`src/components/organisms/`, `src/data/`）。
3. **色の確定（最重要の経験則）**: 色に関する指摘は次の優先順で値を確定する。
   1. **`diffList` に具体値（hex 等）が書かれていればそれが正**。サンプリングは不要。
   2. 具体値が無い場合のみ、**目視で判断せず**サンプリングする。スクリーンショット画像では近似色（ごく薄い色と白など）が目視でほぼ区別できないことがある。**python3 + Pillow で画像の該当ピクセルの RGB を直接サンプリングして hex を確定する**:
   ```bash
   python3 - <<'PY'
   from PIL import Image
   im = Image.open("<imagePath>").convert("RGB")
   print('#%02X%02X%02X' % im.getpixel((x, y)))
   PY
   ```
   - 画像がツールの表示解像度と異なる場合、表示座標に**倍率をかけて元画像の座標に変換してから**サンプリングする。
   - 確定した hex は、まず対象プロトタイプの `src/index.css` の `@theme` ブロックにあるトークン（`--color-*`）と突き合わせ、一致するトークンがあればそれを使う（例 `bg-blue-2`）。
   - 一致するトークンが無い場合は、同一プロトタイプ内の類似画面で直値参照 `bg-[#xxxxxx]` ＋ デザイン変数名のコメントを付ける既存パターンがあれば、それに倣う。無ければ同じ形式（直値 + コメント）で新規に追加する。
4. **実装**: `diffList` の指摘を1件ずつ、既存コンポーネント・トークン・命名パターンを再利用しながら修正する。新規抽象化は最小限にとどめ、コメントは「なぜ」が非自明な箇所にのみ書く。
5. **検証**: `cd prototypes/<proto> && pnpm run lint && pnpm run build` を実行し、両方パスすることを確認する。失敗した場合は原因を修正し再実行する。
6. **未解決点**: 指摘の意図が曖昧、画像から判断できない、または既存実装のどこを直せば良いか特定できない項目は、**推測で実装せずスキップ**し、理由付きで最終報告に載せる。途中で作業を止めて質問しない。対応できた項目だけで完了してよい。

## 報告（既定フローの終点。スクショは撮らない）

以下を1つの報告にまとめる:

1. **相違点対応表**:

   | # | 相違点リストの項目 | 対応 | 補足（使用トークン・確定 hex 等） |
   | - | ------------------ | ---- | --------------------------------- |

2. 表に続けて:
   - 変更ファイル一覧
   - 未対応項目とその理由
   - リスト外で気づいたが手を付けなかった差異（対応するかは人間が判断）
   - **ブラウザ確認用 URL**: `http://localhost:<port><route>`（port は対象プロトタイプの `vite.config.ts` が権威。dev サーバー未起動でも、スクショ目的での起動はしない）
   - 参照画像（`imagePath`）のパス（人間が見比べる際の材料として）
3. 末尾に1行添える: *見た目の確認はブラウザで行ってください。修正指示はまとめて1メッセージで、実値つきでお願いします（例: 「#2 ヘッダーの gap を 16px に、#5 背景を bg-blue-2 に」）。AI によるスクショ比較が必要な場合は `/verify-design-diff` を実行してください。*

数値プロパティ（余白・フォント・色）は、コード上の現在値（Tailwind クラス / hex）を必ず併記する。人間はデザイン側の値と見比べるだけで判断できる。

## 制約

- **Figma 系 MCP ツール（`mcp__figma-*` / `mcp__plugin_figma_*` 等）は一切呼び出さない。** 見えていても無視する。
- コミット・push は行わない（人間の役割。必要なら `/commit` を別途実行する）。
- 実装後の画面スクリーンショット取得・視覚比較は行わない（`/verify-design-diff` の担当）。
- 作業用の一時スクリプト（ピクセルサンプリング等）は一時ディレクトリに置き、完了後に削除する。プロジェクトディレクトリ配下にゴミファイルを残さない。
- 担当外の画面・ファイルは読み書きしない。dev サーバーは起動しない。
