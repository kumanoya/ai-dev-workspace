# commit — コミット規約と手順

現在の未コミット変更を1件のコミットにまとめる。push はしない。

## 手順（コスト配慮: ツール呼び出しは最小限に）

1. `git branch --show-current` と `git status --short` を**1回**で確認する（`&&` で連結してよい）。
   - ブランチが `main` なら**何もせずに中断**し、フィーチャーブランチの作成を提案する。
   - 変更が無ければ中断する。
2. 差分の把握は `git diff --stat`（+ 未追跡ファイルは status で把握）を基本とし、メッセージ作成に内容確認が必要なファイルだけ `git diff -- <path>` を個別に見る。**全文 diff の一括取得はしない**。
3. コミット対象のパス指定がチャットメッセージにあればそのパスのみ、なければ関連する変更を `git add` する。`.env` や認証情報らしきファイルが含まれていたらステージせず、報告する。
4. 下記のメッセージ規約に従い、heredoc でコミットする（`git commit -m "$(cat <<'EOF' ... EOF)"`）。

## メッセージ規約

prefix は Conventional Commits の標準語彙（英語）、要約・本文は**日本語**。

```
<type>: <変更内容の要約>

- 変更点
- 理由・影響範囲

Co-Authored-By: GitHub Copilot (<実行モデル名>) <noreply@github.com>
```

### type の一覧

| type | 用途 |
|---|---|
| `feat` | 機能追加 |
| `fix` | バグ修正 |
| `docs` | ドキュメントのみの変更 |
| `style` | 整形のみ（挙動不変。フォーマット・空白・セミコロン等） |
| `refactor` | 挙動を変えないコード整理 |
| `perf` | パフォーマンス改善 |
| `test` | テストの追加・修正 |
| `build` | ビルド・依存関係（`package.json`、Vite/TS 設定等） |
| `ci` | CI 設定 |
| `chore` | 上記に当てはまらない設定・雑務 |

### 書式ルール

- `<type>` は**小文字**、直後は `: `（半角コロン + 半角スペース）
- **scope は使わない**（`feat(v2):` のような括弧付きは書かない）。対象が特定パッケージなら要約文の中で示す（例: `feat: sample-app-v2 に検索画面を追加`）
- 要約は日本語で体言止めまたは連用形、末尾に句点を付けない
- 破壊的変更は `feat!:` のように `!` を付け、本文に `BREAKING CHANGE: <内容>` 行を書く
- Co-Authored-By の実行モデル名は**実際にコミットを作成したモデル**（例: `Claude Haiku 4.5`）を入れる

### type が割れるときの判定

- `specs/` の仕様更新は `docs`
- コードとドキュメントが混ざるコミットは**コード側の type** を採る

## 制約

- **push・pull・fetch・merge・rebase・amend・reset・checkout は禁止**。コミット作成のみ（push は人間が差分確認後に行う）。
- `main` ブランチへのコミット禁止（手順1で中断）。
- ステージ済みの他の変更を巻き込まない: 対象パスの指定があるときはそのパス以外を `git add` しない。
- ファイルの作成・編集・削除は一切しない。コマンド実行は git 操作に限る。
